# Benchmark Evaluation Specification and Metric Definitions
**Phase 5: Research Foundation and Benchmark Preparation**
**Project:** AI-Wireless Copilot
**Date:** November 2026

---

## 1. Experimental Methods

The evaluation framework is designed to compare four progressive experimental methods:

- **M1: Direct LLM Prompting**
  The user's natural language request is passed directly to the LLM with a system prompt specifying the output JSON schema. No external knowledge, validation, or verification is applied beyond parsing the JSON string.
- **M2: LLM + RAG**
  The user's prompt is augmented with top-$k$ retrieved excerpts from the domain knowledge base (`rag/knowledge_base/wireless_basics.md`) before LLM configuration extraction. No validation or verification is applied.
- **M3: LLM + RAG + Physics-Aware Validation**
  The configuration extracted by M2 is subjected to deterministic physics-aware validation rules before execution (checking for physical contradictions, SNR convention mismatches, and finite-sample size adequacy). If invalid, at most one bounded correction attempt is supplied to the LLM. No post-simulation verification is applied.
- **M4: M3 + Independent BER Verification**
  The simulation output generated by M3 is independently validated post-execution against analytical communication bounds and statistical confidence intervals (exact two-sided Clopper-Pearson 95% CI and Rule-of-Three for zero-error observations). If the simulation deviates beyond statistical tolerance or suffers from sample starvation, the result is flagged or rejected.

> [!IMPORTANT]
> **Implementation Scope Note:** Phase 5 establishes the mathematical foundations, metric definitions, benchmark datasets, and experiment configuration schemas. Defining schemas and experiment runners is **not** equivalent to a completed M1–M4 evaluation. The empirical execution of M1–M4 across foundation models is planned for Phase 6. Remote Mistral 7B experiments are designed for future execution on Kaggle GPU / DGX and are not claimed as completed in Phase 5.

## 2. Core Evaluation Metrics

Let $N_{\text{total}}$ denote the total number of test cases in the benchmark dataset ($N_{\text{total}} = |D|$).
Let $D_{\text{exec}} \subseteq D$ denote the subset of cases whose ground truth action is `execute` ($N_{\text{exec}} = |D_{\text{exec}}|$).
Let $D_{\text{reject}} \subseteq D$ denote the subset whose ground truth action is `reject` or `clarify` ($N_{\text{reject}} = |D_{\text{reject}}|$), where $D = D_{\text{exec}} \cup D_{\text{reject}}$ and $D_{\text{exec}} \cap D_{\text{reject}} = \emptyset$.

---

### Metric 1: Configuration Validity Rate (CVR)
Measures syntactic and API schema conformity. A configuration is *schema-valid* if it parses as valid JSON, contains all mandatory fields, matches expected types, and falls within allowable API ranges (e.g., $N_{\text{bits}} \ge 1000$, $\text{snr\_stop} > \text{snr\_start}$).

$$\text{CVR} = \frac{N_{\text{schema\_valid}}}{N_{\text{total}}}$$

- **Population:** All evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Numerator ($N_{\text{schema\_valid}}$):** Number of test cases that yield a syntactically valid JSON configuration conforming to `SimulationRequest`.
- **Denominator ($N_{\text{total}}$):** Total number of evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Aggregation:** Proportion in $[0.0, 1.0]$ or percentage.
- **Handling:** Every prompt in the benchmark is included. If the model output cannot be parsed as valid JSON or violates schema constraints, it scores 0.

---

### Metric 2: Physical Correctness Rate (PCR)
Measures whether the configuration faithfully and accurately adheres to physical reality and the intended request:
1. For executable cases ($i \in D_{\text{exec}}$): All extracted parameters match the ground-truth physical parameters (modulation, channel, correct SNR convention, non-contradictory parameters, and adequate Monte Carlo bit count).
2. For non-executable cases ($i \in D_{\text{reject}}$): The system correctly identifies the request as invalid, contradictory, or unsupported, rather than silently creating an executable configuration.

$$\text{PCR} = \frac{\sum_{i \in D} \mathbb{I}(\text{Case } i \text{ is Physically Correct})}{N_{\text{total}}}$$

where:
$$\mathbb{I}(\text{Case } i \text{ is Physically Correct}) = \begin{cases}
1, & i \in D_{\text{exec}} \land \text{ConfigMatchesPhysicalGroundTruth}(i) \\
1, & i \in D_{\text{reject}} \land \text{SystemRefusesOrRejects}(i) \\
0, & \text{otherwise}
\end{cases}$$

- **Population:** All evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Numerator:** Sum of physically correct decisions across both executable and rejected cases (programmatically derived by `classify_case_result()`).
- **Denominator:** Total number of evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Aggregation:** Proportion in $[0.0, 1.0]$ or percentage.

---

### Metric 3: Silent-Error Rate (SER)
**Central Research Metric:** Measures instances where the pipeline successfully runs (HTTP 200, exit code 0) and returns a simulation result, but the output is **scientifically invalid, physically contradictory, or statistically unsound** without being detected or flagged.

$$\text{SER} = \frac{N_{\text{silent\_errors}}}{N_{\text{total}}}$$

- **Population:** All evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Numerator ($N_{\text{silent\_errors}}$):** Number of cases where an invalid, corrupted, or statistically starved result was returned without substantiated system validation or verification flags. Derived programmatically by `classify_case_result()`: a caller-provided boolean cannot suppress silent error without supporting validation or verification records.
- **Denominator ($N_{\text{total}}$):** Total number of evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Aggregation:** Proportion in $[0.0, 1.0]$ or percentage.
- **Distinction between Flagged and Silent Errors:**
  If the system detects an error, logs a warning, returns an error status code, or requests user clarification, it is **NOT** a silent error. A silent error occurs **strictly and only** when the system claims successful completion while returning an invalid result.

A case is classified as a **Silent Error** if ANY of the following occur without system detection:
1. **Unflagged Convention Shift:** Prompt specifies $E_s/N_0$, but simulator executes at $E_b/N_0$ without offset compensation (e.g., 3.01 dB shift for QPSK).
2. **Physical Contradiction Execution:** Request has incompatible parameters (e.g., Rician $K$-factor with AWGN channel; non-coherent detection request executed with coherent MRC) but executes successfully anyway.
3. **Statistical Starvation / Zero-Error Fallacy:** Simulation runs at high SNR with inadequate sample size, produces 0 bit errors, and reports $\text{BER} = 0.0$ as an exact measurement without uncertainty bounds.
4. **Unsupported Feature Coercion:** Prompt requests an unsupported modulation (e.g., 16-QAM or 64-QAM) or channel (e.g., Nakagami-$m$), but the system silently falls back to BPSK/AWGN and executes without explicit warning.
5. **Execution of Invalid / Malicious Prompt:** Prompt is ambiguous, contradictory, or adversarial, but the system manufactures a default configuration and executes.

---

### Metric 4: Task Completion Rate (TCR)
Measures overall end-to-end task decision accuracy.

$$\text{TCR} = \frac{N_{\text{correct\_decision}}}{N_{\text{total}}}$$

- **Population:** All evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Numerator ($N_{\text{correct\_decision}}$):** Count of cases where `actual_decision == expected_action`.
- **Denominator ($N_{\text{total}}$):** Total number of evaluated benchmark prompts ($N_{\text{total}} = 78$).
- **Aggregation:** Proportion in $[0.0, 1.0]$ or percentage.
where a decision is correct if:
- For an executable prompt: The system executes the simulation with physically valid parameters.
- For an incomplete/ambiguous prompt: The system correctly requests clarification.
- For an invalid/unsupported/adversarial prompt: The system correctly rejects the request.

> [!NOTE]
> Distinguishing a **correct rejection** from a **failed execution** is fundamental. Refusing to run an unphysical request (e.g., negative bit count or 256-QAM on an engine that only supports BPSK/QPSK) is scored as **successful task completion** ($+1$), not a failure.

---

### Metric 5: BER Verification Error (BVE)
Evaluates numerical agreement between simulated BER and theoretical analytical ground truth for cases where a closed-form reference is valid ($D_{\text{valid\_ref}} \subseteq D_{\text{exec}}$):

$$\text{BVE} = \frac{1}{|D_{\text{valid\_ref}}|} \sum_{i \in D_{\text{valid\_ref}}} \frac{1}{|K_i|} \sum_{k \in K_i} d\left(p_{\text{sim}}(i, k), \; p_{\text{theo}}(i, k)\right)$$

where $K_i$ is the set of SNR evaluation points for case $i$, and the distance function $d(p_{\text{sim}}, p_{\text{theo}})$ is exhaustively defined across all four edge-case domains:

$$d(p_{\text{sim}}, p_{\text{theo}}) = \begin{cases}
\left| \log_{10}(p_{\text{sim}}) - \log_{10}(p_{\text{theo}}) \right|, & p_{\text{sim}} > 0 \land p_{\text{theo}} > 0 \\
\left| \log_{10}\left(\frac{3}{N_{\text{bits}}}\right) - \log_{10}(p_{\text{theo}}) \right|, & p_{\text{sim}} = 0 \land p_{\text{theo}} > 0 \\
D_{\text{penalty}} = 4.0, & p_{\text{sim}} > 0 \land p_{\text{theo}} = 0 \\
0.0, & p_{\text{sim}} = 0 \land p_{\text{theo}} = 0
\end{cases}$$

- **Domain 1 ($p_{\text{sim}} > 0, p_{\text{theo}} > 0$):** Standard decade-scale logarithmic discrepancy.
- **Domain 2 ($p_{\text{sim}} = 0, p_{\text{theo}} > 0$):** Zero-error observation under positive theoretical expectation. The undefined naive logarithm $\log_{10}(0) = -\infty$ is replaced by the one-sided 95% Rule-of-Three upper bound $\frac{-\ln(0.05)}{N_{\text{bits}}} \approx \frac{3}{N_{\text{bits}}}$, mathematically penalizing finite-sample starvation.
- **Domain 3 ($p_{\text{sim}} > 0, p_{\text{theo}} = 0$):** Positive simulated error rate when theoretical expectation is strictly zero. Assigned fixed penalty $D_{\text{penalty}} = 4.0$ (equivalent to a 4-decade / 10,000x error).
- **Domain 4 ($p_{\text{sim}} = 0, p_{\text{theo}} = 0$):** Perfect agreement between simulation and zero-error analytical expectation ($d = 0.0$).
- **Population:** Executable benchmark cases with valid analytical reference solutions ($D_{\text{valid\_ref}}$).
- **Numerator:** Sum of per-point distance values across all SNR points and cases.
- **Denominator:** Total number of evaluated SNR points across cases in $D_{\text{valid\_ref}}$.
- **Aggregation:** Mean decade deviation in $[0.0, \infty)$.
- **CI Coverage Rate:** Additionally, we record the percentage of simulated points where the theoretical BER falls within the exact two-sided 95% Clopper-Pearson confidence interval:
  $$\text{CI}_{95}\text{ Coverage Rate} = \frac{\sum_{i, k} \mathbb{I}\left( p_{\text{theo}}(i, k) \in [p_{\text{low}}(i, k), p_{\text{high}}(i, k)] \right)}{\sum_i |K_i|}$$

---

### Metric 6: Latency Overhead (LO)
Measures the computational delay introduced by each pipeline stage without double-counting overlapping operations:

$$T_{\text{total}} = T_{\text{RAG}} + T_{\text{LLM\_extract}} + T_{\text{validation}} + T_{\text{simulation}} + T_{\text{verification}} + T_{\text{overhead}}$$

- **Timing Discipline:** Each individual stage latency ($T_{\text{RAG}}$, $T_{\text{LLM\_extract}}$, $T_{\text{validation}}$, $T_{\text{simulation}}$, $T_{\text{verification}}$) is timed sequentially and non-overlapping using high-resolution monotonic clocks (`time.perf_counter()`).
- **Independent Total Measurement:** Total wall-clock latency $T_{\text{total}}$ is measured by an enclosing timer from pipeline request receipt to response emission ($T_{\text{total}} \ge \sum T_{\text{stage}}$). Any inter-stage serialization, task handoff, or event loop delay is captured as $T_{\text{overhead}} = T_{\text{total}} - \sum T_{\text{stage}}$.
- **Latency Overhead Definition:** $\text{LO} = T_{\text{total}} - T_{\text{simulation}}$
- **Population:** Evaluated exclusively on cases that execute through the pipeline ($D_{\text{exec\_actual}}$).
- **Aggregation:** Reported as median, mean, and 95th percentile ($p_{95}$) across runs in seconds.

## 3. Summary of Evaluation Rules

| Metric | Code | Target Direction | Population | Handling of Excluded / Non-Applicable Cases |
|---|---|---|---|---|
| **Configuration Validity Rate** | CVR | Higher $\uparrow$ | All cases ($N_{\text{total}}$) | None excluded. Invalid JSON / schema errors = 0. |
| **Physical Correctness Rate** | PCR | Higher $\uparrow$ | All cases ($N_{\text{total}}$) | Correct rejection counts as correct (1). |
| **Silent-Error Rate** | SER | Lower $\downarrow$ | All cases ($N_{\text{total}}$) | Flagged errors are NOT silent errors. |
| **Task Completion Rate** | TCR | Higher $\uparrow$ | All cases ($N_{\text{total}}$) | Rejections of invalid prompts count as completion. |
| **BER Verification Error** | BVE | Lower $\downarrow$ | Cases with valid analytical ref ($D_{\text{valid\_ref}}$) | Excluded if no analytical formula exists or if prompt was rejected. Zero errors mapped to Rule of Three bound. |
| **Latency Overhead** | LO | Lower $\downarrow$ | Executed cases | Partitioned by stage; non-overlapping. |
